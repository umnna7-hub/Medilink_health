Isolated Security Labs

These are local demonstrations, not production controls. Use only synthetic data and run the web apps on loopback. Do not bind them to a public interface, connect them to hospital systems, or use real patient records.

SQL query handling

vulnerable_app.py is intentionally unsafe for controlled classroom analysis; it listens on 127.0.0.1:5001 and uses the local SQLite lab database. secure_app.py listens on 127.0.0.1:5002, validates a positive integer, selects only needed columns, and binds the ID as a query parameter.

Validation rejects malformed inputs but is not a replacement for parameterized queries. The MySQL grants in the repository's create_app_user.sql are a separate production-account template; review and apply them only to the intended isolated MySQL database. They do not configure the SQLite lab.

SQL injection fix comparison (Task 3)

sqli_comparison.py serves the same two lookups (by patient ID and by name) through five variants so each defence can be judged alone: vulnerable, validation_only, parameterized_only, least_privilege_only and combined. It uses a temporary SQLite database of synthetic records, including a fake staff_accounts table that an attacker should never reach.

Least privilege is simulated with a read-only SQLite connection plus an authorizer that allows reading only the patients table (SQLite has no accounts; on MySQL the equivalent is GRANT SELECT on the needed tables only, as in create_app_user.sql).

Run the full comparison with:

powershell
python .\sqli_demo.py             # plain-text table
python .\sqli_demo.py --markdown  # Markdown table to paste into the report

What the results show:

Validation only blocks these payloads but depends on guessing what bad input looks like. A strict name allow-list also rejects legitimate names such as Liam O'Brien, and any mistake leaves the SQL concatenation exposed.
Parameterized queries treat every payload as plain data and keep legitimate names working. This is the primary fix.
Least privilege alone does not stop injection (the tautology still dumps every patient) but limits the damage: the UNION attack on staff_accounts is refused by the database.
Combined (format checks, bound parameters, least privilege) stops every attack, keeps O'Brien working, and returns no database error text.

To explore the endpoints manually, run python .\sqli_comparison.py (loopback port 5004) and request, for example, /vulnerable/patient?id=1 or /combined/search?name=....

Rate-limit and integrity demonstrations

rate_limiter.py listens on 127.0.0.1:5003. Its in-memory per-process counter demonstrates a simple threshold and rapid-request alert; it is not distributed DDoS protection.

The backup demo encrypts each backup with Fernet using BACKUP_KEY and authenticates a manifest with a separate BACKUP_MANIFEST_KEY. Set both keys in the process environment; neither key is generated by the script or written to a file. BACKUP_DIR selects the backup destination and defaults to secure_backups under this directory.

The destination can be a location you manage as offline storage, but selecting a separate folder does not make it immutable. An attacker who can access both the backup and the key environment can still replace the data and its authentication. Production recovery requires independently controlled, immutable/offline copies and scheduled restore tests.

Files left in secure_backups by the previous plaintext-backup implementation are not read by this version and are not protected by the new format. Verify they are no longer needed before removing them.

From this directory, create and restore a backup with:

powershell
python .\backup_recovery.py create
python .\backup_recovery.py restore

Run the corruption-and-recovery drill with:

powershell
python .\drill.py

The drill uses a temporary subdirectory under BACKUP_DIR and temporary source data, then removes those files. It requires both environment keys.

Rule-based monitoring prototype

monitor.py reads the Flask backend log and the existing vendor_audit_log.jsonl. The backend writes to LOG_FILE; by default this is backend/app.log. Set the same LOG_FILE value when running the backend and monitor. From this directory, run:

powershell
python .\monitor.py

Alerts are appended to alerts.jsonl. The rules use recent log timestamps for these thresholds: 5 failed logins per email in 5 minutes, 20 HTTP 429 responses per IP in 1 minute, one SQL-marker URL in 1 minute, and more than 3 denied privileged actions per vendor/action in 10 minutes. SQL-marker alerts omit the raw URL. This is a rule-based prototype, not a SIEM or a replacement for centralized, tamper-resistant monitoring.

Local failover simulation

Run python .\failover_sim.py from this directory to start health endpoints on 127.0.0.1:5101 and 127.0.0.1:5102, then execute 20 local failover trials. It prints and saves the measured min/mean/max to failover_results.json. The output is labeled LOCAL SIMULATION, not production availability.

Focused tests

Run from this directory:

powershell
python -m unittest discover -s . -p "test_*.py"

The tests cover the SQL injection comparison, validation and parameterized lookup behavior, the local rate-limit threshold, and fail-closed HMAC, ciphertext-integrity, and decryption checks. The SQL injection tests send sample payloads only to a temporary SQLite database of synthetic records through Flask's in-process test client. No test opens a network port or touches any other system.
